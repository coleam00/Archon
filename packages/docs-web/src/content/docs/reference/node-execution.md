Archon captures a node's execution facts in `nodeExecutionRecordSchema`. The shared public facts use `nodeExecutionMetadataSchema`; cache decisions use `nodeCacheRecordSchema`. Their source is [`packages/workflows/src/schemas/node-execution.ts`](https://github.com/coleam00/Archon/blob/dev/packages/workflows/src/schemas/node-execution.ts). The generated tables below come from these schemas and the separate persisted projection, `serializedNodeDataSchema` in [`node-record-serialization.ts`](https://github.com/coleam00/Archon/blob/dev/packages/workflows/src/node-record-serialization.ts).

## Identity and execution context

The node descriptor identifies the authored node and its kind; `path` identifies its location in the run, including composed structure. An invocation identifies the logical execution, while an attempt identifies one execution attempt within it. Retrying can create another attempt without creating another invocation. `invocation.loopPath` identifies enclosing loop groups and iterations.

The invocation's checkout observation captures the checkout at its first attempt. Later attempts and resumed continuations retain it; each attempt can also have its own checkout observation. An observation describes Git content, a positively established non-Git directory, or an unavailable observation. It is evidence, not a policy against dirty starts.

The binding records the provider, requested model, provider-resolved model, tier, effort, session preview, and session origin when available. Requested and resolved models are distinct: Archon does not substitute the requested model for an unreported resolved model. A session preview is for display, not a resume token. The full `sessionId` is excluded by `executionMetadata`; the durable `session_id` is not a public session-resume token surface.

Timing describes the attempt's start and observed duration. Lifecycle describes start, completion, failure, skip, or suspension. Output can carry runtime text, structured output, declared output paths, and persisted preview/truncation/spill provenance. Diagnostics carry additional execution observations; they are excluded from shared execution metadata along with output and the full session ID.

## Measurements and accounting

A measurement is either a reported value (`source: provider`) or explicitly unavailable. A genuine reported zero is a value; absence never becomes zero. `startNodeExecution` initializes availability from provider capabilities: `unsupported` means the provider declares no support, `not_reported` means support is declared but no value arrived, `unknown` means support is undeclared, and `not_applicable` means no provider call happened: the node has no provider, or the attempt failed before calling it. `finishNodeExecution` retains availability for omitted observations and marks rejected token or non-finite numeric observations `invalid`. An explicit provider `tokensUnknown` signal marks token accounting `incomplete`: at least one paid interval cannot be counted, so retries, resumed loops, and run or fan-out totals stay unavailable while cost continues to accumulate. Ordinary omitted measurements do not invalidate a token total.

The [provider capability matrix](/reference/provider-capabilities/) is the per-provider reporting reference. Support does not guarantee a value on every result or complete nested-agent usage. Archon does not estimate cost or infer turns from event counts.

`nodeCostScope` maps `accounting: node` to `own` and other accounting kinds to `total`. Historical rows fall back to `aggregate: true` for `total`, otherwise `own`. This scope is a projection rule, not an execution-record field. A total restates spend that other rows may carry, so summing every event double-counts it.

The engine's resume fold treats composed-instance terminal usage as authoritative for the segment preceding that terminal: its inner observability rows can be missing after a crash. Inner spend after the last terminal remains counted until a later terminal closes that segment. Other aggregate rows restate leaf usage. Use engine-produced run totals rather than constructing an independent client aggregation rule.

### Reading tokens and cost

Workflow JSONL `node_complete.tokens` and persisted `node_completed.data.tokens` use `input`, `output`, and optional `cacheRead` / `cacheWrite` fields. `input` is gross prompt input, including cache reads and cache writes. When both cache fields are present, uncached input is `input - cacheRead - cacheWrite`. An absent cache field means the provider did not report it; `0` means the provider reported zero. Which rows carry the field at all depends on the sink: the transcript carries it only on a row that reports its own spend, while newly emitted persisted rows carry it on every `node_completed` row except a `loop_group` roll-up and a row whose token count is incomplete (see below). So a sum over `node_completed.data.tokens` counts a composed fan-out's scope once per level, and `data.accounting` names each row's role. Run metadata exposes the same totals as `total_tokens_in`, `total_tokens_out`, `total_cache_read_tokens`, and `total_cache_write_tokens`. A cache total sums every contributing node that reported that axis; when at least one node did not, the total is a **floor** and the aggregate carries `cachePartial: true` (run metadata: `total_cache_partial`). So `input - cacheRead - cacheWrite` is exact when `cachePartial` is absent and an upper bound on full-price input when it is set. An axis no node reported stays absent, and cache usage in records created before this contract cannot be recovered.

Read cost from `cost_usd`, not from the token counts. Because `input` is gross, pricing a node by hand means getting four axes and the cache rates right; `cost_usd` is the number the provider itself reported. A row reports it as its own only when the row's `accounting` is `node`, and no row restates another row's spend, so summing the cost the transcript's rows report as their own reproduces the run's own cost. Count error rows in that sum: a retried attempt that already spent reports on its own `node_error` row. A row that restates spend its scope already reports elsewhere in the same run (a `loop_group` roll-up over its body rows, a composed fan-out wrapper over its instances, an instance terminal over its own leaves) omits both usage fields from its transcript row and names itself in `execution.accounting` instead. The persisted `node_completed` row keeps `cost_usd` on every row and marks a restatement with `data.aggregate: true`; a resume skips a marked row because its scope's own rows already carry that spend, except a composed-instance terminal, which the resume keeps as the authoritative source for the preceding inner segment (#3508). Later inner spend remains counted until the next terminal closes its segment. JSONL `workflow_complete` carries the successful run's totals as `cost_usd` and `tokens`; a DAG-owned terminal `workflow_error` carries the same aggregate when work reported usage before failure. These match run metadata `total_cost_usd` and `total_tokens_*`, except that an incomplete token count leaves `tokens` off both rows (see below). On a row that reports its own spend, an absent `cost_usd` means the provider reported no cost (Codex reports none), while `0` means it reported zero. On a restatement row an absent `cost_usd` means the scope's spend is on the rows that row names.

Claude reports a session's running total, so Archon subtracts the source session's total from its native session transcript when a node resumes or forks, including across Archon processes. If that persisted state is missing or invalid, the earlier total is unknown and the first result's cost is absent rather than over-counted. Later results can report incremental cost from the newly known baseline, so the node's `cost_usd` can be a partial cost that excludes the first interval. Claude tokens cover the main agent, forked skills, and subagents included in that cost: input (including cache reads and writes), output, cache read, and cache write. Fresh sessions report the full totals; resumes and forks subtract the persisted baseline on all four axes. If the token baseline is missing or incomplete (including older transcripts that stored only output tokens or positive cost with no model totals), or totals are inconsistent, token usage is absent and Archon logs `claude.query_tokens_unknown`. Tokens remain unknown for the rest of that query, even if later results supply usable totals. The node's tokens also remain absent across structured-output reasks and later loop iterations after an unknown interval; cost subtraction continues independently.

OpenCode prices each model step as its own assistant message, so an OpenCode node's cost and tokens sum every assistant message its prompt produced, such as the steps before and after a tool call.

Newly emitted incomplete counts are recorded, not dropped: the node's `execution.spend.tokens` (persisted as `data.spend.tokens`) is `{ "source": "unavailable", "reason": "incomplete" }` and the row carries no `tokens`. Every total containing that node, through retries, loops, fan-outs, composed instances, child runs, and resume, is incomplete too: the containing rows omit `tokens`, and run metadata sets `total_tokens_unknown: true` with `total_tokens_in`, `total_tokens_out`, `total_cache_read_tokens`, `total_cache_write_tokens`, and `total_cache_partial` set to `null`. Cost totals keep summing every reported cost. Do not sum `tokens` across rows as a run total when any row is incomplete.

Historical records are not rewritten when read. On resume, a counted event with malformed required `tokens.input` or `tokens.output` makes the run total unknown even if that event still has a `tokens` object and no explicit `incomplete` spend marker. Aggregate restatements excluded from accounting do not make the total unknown. Child-run metadata re-entry also treats missing or malformed required counters as unknown when either counter is present. A present `total_tokens_unknown` marker other than `false`, including `null` or a string, keeps child tokens unknown even when both counters are numeric. The containing run records `total_tokens_unknown: true` and null token counters; cost and lifecycle are preserved.

An interactive loop resumed from its gate continues the cost the paused iterations spent. When that carried-in cost is not known complete (a gate paused by a build before execution metadata, or one whose recorded cost was unavailable or partial), the loop's row records `spend.costUsd.partial: true` once later iterations report cost, and its `cost_usd` is a floor.

A run that spent nothing on AI, such as a bash-only workflow, carries no `cost_usd` rather than `0`. Governance nodes do not yet have complete terminal transcript-row coverage, so read usage from the rows that exist rather than treating an absent row as zero spend.

## Cache decisions and skips

Cache decisions carry no new attempt, provider binding, timing, or newly consumed spend. `serializeNodeStateRecord` projects them as follows. The workflows conformance test checks these action-to-event names against the serializer:

- Replayed: `node_skipped_prior_success`, with the reusable output under the normal output keys.
- Reset: `node_always_run_reset`, with prior output and its truncation/spill provenance under `prior_*` keys.
- Invalidated: `node_prior_cache_invalidated`, with prior output, prior structured output when present, `reason: stale_dependency`, and `invalidating_deps`.

A skipped execution instead carries a lifecycle reason and typed `cause`. The cause identifies condition evaluation, a condition parse error, timeout, or an upstream failure/skip with its origin. Cache records and skip lifecycle records are separate contracts.

## Where the facts are exposed

| Surface | Payload |
| --- | --- |
| `archon workflow get <run-id> --json` | Run and terminal information; no full execution record |
| `archon workflow get <run-id> --json --verbose` | Node summaries with execution metadata reconstructed from durable events when present |
| `archon workflow get <run-id> --json --verbose --events` | Durable event envelopes and serialized `data` |
| `GET /api/workflows/runs/{runId}` | Serialized events, with event-level `cost_scope` when `data.cost_usd` is numeric; separate run terminal/node summaries |
| Live emitter and JSONL transcript | Shared `executionMetadata`, excluding output, diagnostics, and the full session ID |

The terminal record's `nodes` are lifecycle summaries from `foldNodeEvents` and `runNodeStateSchema`, not embedded full execution metadata. A `workflow:` fan-out node's summary also carries `fan_out_outcome`, the per-slot record its `node_completed` or `node_failed` event persisted as `data.fan_out_outcome` (`diagnostics.fanOutOutcome` on the execution record). Historical rows may lack execution metadata. See the [API reference](/reference/api/#runs) for the detail endpoint and the [CLI reference](/reference/cli/) for command options.

## Persisted data and resume compatibility

`recordNodeState` serializes a captured record into durable events and derived transcript/emitter facts. The durable projection keeps both nested execution facts and existing flat wire keys. Event envelopes supply run identity, node path, and event type; the persisted-data table below describes `data`, not the envelope or a full in-memory execution record.

[`getDagResumeSnapshot`](https://github.com/coleam00/Archon/blob/dev/packages/core/src/db/workflow-events.ts) reads ordered persisted events through [`readNodeRecordEvent`](https://github.com/coleam00/Archon/blob/dev/packages/workflows/src/node-record-reader.ts). It restores unfinished invocation metadata and completion metadata, reusable completion output, truncation and spill provenance, structured output, declared output paths, and accounting/usage. Legacy `declared_fields` are converted to root output paths when `declared_output_paths` is absent. Failed rows can contribute usage without becoming reusable success. Cache replay inherits reusable completion facts and contributes no new spend; reset and invalidation remove reusable output.

The reader reconstructs lifecycle from the event type and the corresponding error, retryability, typed failure, skip reason/cause, or suspension point. If modern execution metadata is present, its required groups must be complete and its lifecycle valid. The persisted projection also carries diagnostics; being readable does not mean every diagnostic drives resume.

`fan_out_instances` is a separate durable event: its `data.instances` restores the first valid instance snapshot for the fan-out wrapper. It is outside the node-record data schema and the tables below.

Persisted keys and event/envelope identities are compatibility contracts. Older rows must remain readable, and older binaries may open the same database. The optional additive `child_usage` key records cumulative usage by child run ID. Older rows retain their node-level spend and reusable output. Resume can recover child baselines from one unambiguous durable child ID; historical multi-child or unidentified increments remain at node scope without invented per-child allocation. When such rows carry nonzero or unknown usage, re-executing their workflow node fails before child dispatch because earlier spend cannot be subtracted safely. Completed output remains reusable. New `child_usage` records provide that attribution, and absent measurements do not erase earlier measured baselines. Malformed present `child_usage` is a read error. See the [database reference](/reference/database/) for persistence context.
