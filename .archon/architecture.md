# Archon architecture

A map of the code as it is, where it is going, and the boundaries that hold while it moves. Product scope and the reasons behind the target live in [`direction.md`](direction.md); this file covers code structure only. Links point at the owning source. When this file and the code disagree, the code wins and this file is the bug.

### Main flows

- **Chat message.** A bundled adapter, the Web adapter ([`server/src/adapters/web.ts`](../packages/server/src/adapters/web.ts)) or a chat plugin process run by the server's chat host ([`server/src/chat-host/`](../packages/server/src/chat-host/), receipts loaded by [`core/src/platforms/chat-plugins.ts`](../packages/core/src/platforms/chat-plugins.ts)) normalizes the message and calls `handleMessage` ([`core/src/orchestrator/orchestrator-agent.ts`](../packages/core/src/orchestrator/orchestrator-agent.ts)). The chat agent acts through typed tools ([`orchestrator/chat-tools.ts`](../packages/core/src/orchestrator/chat-tools.ts)). `invoke_workflow` queues a launch that the orchestrator dispatches after the turn, resolving the workspace through `validateAndResolveIsolation` ([`orchestrator/dispatch/isolation-resolver.ts`](../packages/core/src/orchestrator/dispatch/isolation-resolver.ts)) and `IsolationResolver` ([`isolation/src/resolver.ts`](../packages/isolation/src/resolver.ts)).
- **Workflow run.** `workflowRunCommand` ([`cli/src/commands/workflow-run-owned.ts`](../packages/cli/src/commands/workflow-run-owned.ts)) or the orchestrator prepares the workspace and submits the run to a `WorkflowHost` ([`core/src/workflows/host-store.ts`](../packages/core/src/workflows/host-store.ts)), backed by SQL ([`sql-host.ts`](../packages/core/src/workflows/sql-host.ts)) or files ([`file-host.ts`](../packages/core/src/workflows/file-host.ts), [`@archon/workflows/file-store`](../packages/workflows/src/file-store/index.ts)). Its engine, `InProcessWorkflowEngine` ([`workflows/src/in-process-engine.ts`](../packages/workflows/src/in-process-engine.ts), port in [`engine-port.ts`](../packages/workflows/src/engine-port.ts)), calls `executeWorkflow` ([`workflows/src/executor.ts`](../packages/workflows/src/executor.ts)), which hands the graph to `executeDagWorkflow` ([`workflows/src/dag-executor.ts`](../packages/workflows/src/dag-executor.ts)). The engine reaches providers and persistence only through `WorkflowDeps` ([`workflows/src/deps.ts`](../packages/workflows/src/deps.ts)): the provider registry and an `IWorkflowStore` ([`workflows/src/store.ts`](../packages/workflows/src/store.ts)).
- **Item.** A start may name the item it belongs to (`--item` on `archon workflow run` and `archon trigger fire`); a fire from inside a run that names none inherits that run's item when it stays in the item's project. The item is one row holding a project key and a key, with no status or position ([`core/src/db/items.ts`](../packages/core/src/db/items.ts)); a run carries its item, and `readItem` ([`workflows/src/item-read.ts`](../packages/workflows/src/item-read.ts)) reads an item's runs, open questions and answers for `archon workflow runs --item` and `GET /api/items`, deriving where it stands each time. One item is worked by at most one run of a workflow at a time: `holdsItem` ([`workflows/src/item-hold.ts`](../packages/workflows/src/item-hold.ts)) owns the rule, and every admission decision (a binding start or drain in `resourceStartBlocker` and `drainableStarts`, a hand start's slot, a pending run's claim, a failed run's resume) reads live runs on items under the one admission lock and applies it, so nothing about the item is stored. A ruling is the second fact on an item: a decision recorded with no question asked (`archon workflow rule`, `POST /api/items/rulings`), kept in an append-only table beside the item ([`core/src/db/item-rulings.ts`](../packages/core/src/db/item-rulings.ts)) where a withdrawal is a row of its own. The read lists rulings in the same timeline as the answers, oldest first, and a run reaches them through the `archon:script` `item()` export; the engine never reads a ruling's text or injects it into a node. A link is the third: an accepted, directed relation from one item to another (`depends_on`, `part_of`, `duplicate_of`; `archon workflow link`), one row per link whose end columns are written once when it is ended, unique while active ([`core/src/db/item-links.ts`](../packages/core/src/db/item-links.ts)). The read lists an item's links from both sides; the engine starts, holds or ranks nothing because of one by itself, and an active `part_of` carries a landing branch (below). A run-ended trigger file with `linked` can start a stage on the items linked to the ended run's item by a kind the file names ([`core/src/db/linked-starts.ts`](../packages/core/src/db/linked-starts.ts), resolved in the transaction that completes the run). An ask is the fourth fact: a decision a completed run left for an operator (`returns: { node, asks }`), opened on the run's item in the transaction that completes the run and closed once by an answer, a withdrawal or a newer set from the same workflow ([`core/src/db/item-asks.ts`](../packages/core/src/db/item-asks.ts)); the engine owns its schema ([`workflows/src/schemas/item-ask.ts`](../packages/workflows/src/schemas/item-ask.ts)) and records `asks_settled` when the last open ask of a set is answered or withdrawn, never when a newer set replaces it; in the same transaction it writes the start of each `on.asksSettled` trigger file that settlement matches ([`core/src/workflows/asks-settled.ts`](../packages/core/src/workflows/asks-settled.ts), [workflow triggers guide](../packages/docs-web/src/content/docs/guides/workflow-triggers.md#start-a-stage-again-when-its-asks-are-answered)). `readItemWindow` ([`workflows/src/item-window.ts`](../packages/workflows/src/item-window.ts)) reads the items of a project with a run started in a window, each through the same assembly as `readItem`, paged by item id under a cursor that pins the window; `archon workflow items`, `GET /api/items/window` and `items()` serialize its page unchanged. The merge of an item's change is the fifth fact, the one that comes from outside: the caller that saw the forge report it records it once (`archon workflow merged`) in its own table keyed by item ([`core/src/db/item-merges.ts`](../packages/core/src/db/item-merges.ts)); the engine never reads a forge payload. A wait is the sixth fact: what a completed run said its item waits for outside Archon (`returns: { node, waits }`), opened on the run's item in the transaction that completes the run and closed once, as a set, when an event meets it, a newer set from the same workflow replaces it, or it is withdrawn ([`core/src/db/item-waits.ts`](../packages/core/src/db/item-waits.ts), schema in [`workflows/src/schemas/item-wait.ts`](../packages/workflows/src/schemas/item-wait.ts)). A source plugin binding with `wake` carries the one normalized event value the wait names, and the item the event names when it names a subject; the transaction that records the receipt claims the delivery, then compares that value as a string with the open waits of the binding's project (on that item, when named), and a match closes the set and writes the start on the wait's item ([workflow triggers guide](../packages/docs-web/src/content/docs/guides/workflow-triggers.md#start-a-stage-when-what-an-item-waits-for-happens)). Nothing fires at a wait's deadline; the attention queue lists an open set past it as `overdue_wait`. A top-level run on an item that completes with an outcome its workflow does not list in `returns.final`, whose end started nothing and that left no ask or wait, stopped its item: the completing write records `item_stopped` in the run's metadata (`finishRun` in [`workflows/src/dag/run-terminal.ts`](../packages/workflows/src/dag/run-terminal.ts)), and the attention queue lists the item as `stopped` while that run is the item's last (`listStoppedItemRuns`); nothing is changed or started by it. The landing branch is the seventh fact (below). An end is the eighth: an operator's statement that nothing more will happen on the item (`archon workflow end`, `POST /api/items/end`), refused while a run, start, ask or wait on it is active ([`core/src/operations/item-ends.ts`](../packages/core/src/operations/item-ends.ts)). It sits in an append-only table with the database's clock at the time ([`core/src/db/item-ends.ts`](../packages/core/src/db/item-ends.ts)) and holds until work starts on the item again: a run created or resumed on it since, a live run, or a queued or held start, so opening writes nothing and run cleanup does not undo it. `readHoldingItemEnd` ([`workflows/src/item-end.ts`](../packages/workflows/src/item-end.ts)) is the one reader: while it holds, the stopped-item queue skips the item and the item read reports it as `ended`. Nothing ends an item by itself. The landing branch is the branch an item's change lands on (`archon workflow landing`), one replaceable row keyed by item ([`core/src/db/item-landings.ts`](../packages/core/src/db/item-landings.ts)). `resolveItemLanding` ([`workflows/src/item-landing.ts`](../packages/workflows/src/item-landing.ts)) is its one reader: the item's own branch, else that of the nearest item it is `part_of` through an active link. `resolveRunLanding` ([`core/src/workflows/item-landing.ts`](../packages/core/src/workflows/item-landing.ts)) checks it on the remote and never creates it; only `createLandingBranch` in the same file, behind `archon workflow landing --from`, creates it, on the same remote and from a start point its caller names. Both start paths (an admitted trigger start in `resource-start-host.ts`, a hand `workflow run` on an item) pass it as the run's `baseOverride`, the channel `--base` uses, so it sets the cut-from and `$BASE_BRANCH` and a continuation keeps its recorded base. A pack declares per-item figures as data in `.shared/item-metrics.json`, and `evaluateItemMetrics` ([`workflows/src/item-metrics.ts`](../packages/workflows/src/item-metrics.ts)) applies their fixed semantics over the window read for `archon metrics --project`. The SQL stores hold items. The file store refuses a start that names one, and every item read.
- **Install hold.** `archon hold set|lift` writes or deletes one row ([`core/src/db/install-hold.ts`](../packages/core/src/db/install-hold.ts)) under the admission lock, and every admission point reads it under the same lock: a binding's completed preparation, a host's queue drain, a hand start's slot and a pending run's claim (for a top-level run nothing admitted). A held binding goes back to pending unprepared, so after the lift the ordinary preparation and `overlap` rules decide it; a held hand start waits in its own process as for a full resource. Running and paused runs never read it.
- **Pause and continue.** A gate, wait, provider usage limit or rate limit that outlasted its retries pauses the run durably and appears in the attention queue as an item. One reader builds that queue for every surface, and an item may or may not have a run behind it ([`workflows/src/attention-queue.ts`](../packages/workflows/src/attention-queue.ts)): an open ask is an item with no run, answered or withdrawn by its ref, and so is a set of waits past its deadline, withdrawn by its ref (`answerAttentionItem`, `withdrawAttentionItem` in [`core/src/operations/attention-items.ts`](../packages/core/src/operations/attention-items.ts)). Approve, reject, answer and abandon go through workflow operations ([`core/src/operations/workflow-operations.ts`](../packages/core/src/operations/workflow-operations.ts)) from any surface, and the continuation host ([`core/src/workflows/continuation-host.ts`](../packages/core/src/workflows/continuation-host.ts)) resumes the run through the shared [`core/src/workflows/continuation-resume.ts`](../packages/core/src/workflows/continuation-resume.ts) path. Provider-limit waits resume when their deadline is due: the reported reset, or a rate limit's backoff. An operator pause (`archon workflow pause`, `pauseWorkflow` in [`core/src/operations/workflow/pause.ts`](../packages/core/src/operations/workflow/pause.ts)) is a request on the running run that the top-level layer walker honours at its next boundary (`runLayers` in [`workflows/src/dag/run-layers.ts`](../packages/workflows/src/dag/run-layers.ts)); the run pauses with `pause_cause: operator`, stays out of the attention queue, and continues only on an explicit resume.
- **Webhooks and triggers.** The server verifies a forge delivery ([`server/src/routes/webhooks.ts`](../packages/server/src/routes/webhooks.ts)) and passes it to the forge adapter's `receiveWebhook` (for GitHub, [`adapters/src/forge/github/adapter.ts`](../packages/adapters/src/forge/github/adapter.ts)). Webhook sources ([`server/src/services/webhook-source-plugins.ts`](../packages/server/src/services/webhook-source-plugins.ts)), schedules and `archon trigger` start workflows without a chat message ([workflow triggers guide](../packages/docs-web/src/content/docs/guides/workflow-triggers.md)).

### Module layout

- **DAG execution.** [`workflows/src/dag-executor.ts`](../packages/workflows/src/dag-executor.ts) keeps the `executeDagWorkflow` entry. The layer walker, node dispatch and shared execution code live in [`workflows/src/dag/`](../packages/workflows/src/dag/), with one folder per node type under [`dag/nodes/`](../packages/workflows/src/dag/nodes/). Each module's tests sit beside it.
- **Chat turn.** [`core/src/orchestrator/orchestrator-agent.ts`](../packages/core/src/orchestrator/orchestrator-agent.ts) keeps the `handleMessage` entry. Request preparation, conversation context, project commands, typed chat tools, workflow dispatch and the AI turn itself live in sibling modules under [`core/src/orchestrator/`](../packages/core/src/orchestrator/). Each module's tests sit beside it, sharing mocks from [`core/src/test/orchestrator-agent-harness.ts`](../packages/core/src/test/orchestrator-agent-harness.ts).
- **HTTP API.** [`server/src/routes/api.ts`](../packages/server/src/routes/api.ts) is an ordered list of per-area registrars, each in an `api.<area>.ts` module beside it.

## Target state

Each item is a direction, not a fact about today's code. The why is in [`direction.md §standalone-core`](direction.md#aspirational-architecture-a-standalone-core).

- **The engine is an SDK.** A public SDK package defines, validates, runs, resumes and queries workflows without the server, the console, adapters, provider implementations or a database. The CLI and console become its first users.
- **Core plus CLI is a complete local install**, with SQLite as the default store, the file store as the minimal one that needs no database, and PostgreSQL as an optional adapter.
- **Integrations are plugins.** Providers, chat platforms and forges attach through their contracts with no provider- or platform-specific branches in engine control flow. The bundled community integrations (Telegram, Discord, Gitea, GitLab, OpenCode and Copilot) move out once their plugin path is proven.
- **Isolation beyond worktrees is plugins.** Containers, VMs and remote execution attach behind `IIsolationBackend`.
- **Lifecycle has pluggable hosts.** Continuations, schedules and triggers are core surfaces that the server, the CLI, an OS timer or a third party can drive.
- **One owner per plugin's config.** Chat and forge plugins follow the single config owner providers already have.
- **Large modules split along their seams** when work touches them, the way the modules under [Module layout](#module-layout) did, following existing patterns rather than a new architecture.

## Boundaries

Rules that hold now and during the move. Each names what enforces it, or says it isn't enforced.

| Rule | Enforced by |
|---|---|
| A package imports only `@archon/*` packages it declares | `check:package-edges` ([`scripts/check-package-edges.ts`](../scripts/check-package-edges.ts)) |
| Which packages may depend on which (the package table above) | `check:package-edges` (`PACKAGE_LAYERING`) |
| `workflows` never imports `core`, `server`, adapters or provider implementations; it gets them through `WorkflowDeps` | `check:package-edges`: the `workflows` row allows none of them at runtime |
| Workflow-facing code in `core` and `cli` reaches persistence only through the workflow host contract | `bun run lint` ([`scripts/check-workflow-persistence.ts`](../scripts/check-workflow-persistence.ts)) |
| Engine schemas use plain `zod`, not `@hono/zod-openapi` | `check:package-edges` |
| CLI startup doesn't load core, the engine or provider SDKs before a command needs them | `check:cli-import-boundary` ([`scripts/check-cli-import-boundary.ts`](../scripts/check-cli-import-boundary.ts)) |
| Provider SDK dependencies live only in `providers`; copied SDK types conform to the SDK | `bun run lint` ([`scripts/check-sdk-type-drift.ts`](../scripts/check-sdk-type-drift.ts)) for the copies. **The location rule is not enforced.** |
| No provider- or platform-specific branches in engine control flow | **Not enforced.** Review only. |
| The console uses only generated API types | Generated path/method transport, `scripts/check-web-api-types.ts` in lint, `check:api-types`, plus `web` declaring no `@archon` dependency |
| Schema changes are additive, and SQLite and PostgreSQL agree | `check:schema-upgrades`, `check:sqlite-vintages`, the schema parity tests in [`core/src/db/adapters/sqlite.test.ts`](../packages/core/src/db/adapters/sqlite.test.ts) |
| Each provider's capabilities are declared once, in its `capabilities.ts`, and the docs derive from them | `check:capability-matrix` |
| Workflow packs don't hardcode a project's context paths, and the engine doesn't assume a pack's conventions | **Not enforced.** Review only. |
