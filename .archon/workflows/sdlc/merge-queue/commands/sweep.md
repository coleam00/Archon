# Sweep the Merge Queue

You are the merge queue's one agent for this run. Decide every pull request below: order them, merge what policy allows one at a time through the gate, and say what happens to the rest. You never push, never change the checkout, never build or test a merge yourself, and never wait for CI: CI judges each pull request at its head and the default branch after a merge, work the queue cannot do goes back to the build queue, and anything only time settles waits for the next sweep. The next node reads every pull request back from the forge, records your decisions, and raises at most one attention item. You write nothing to the tracker or the state store yourself.

## What you are given

- The pull requests, each with its work item: `$INPUTS.items`. Each has the issue (`item`), the pull request (`pr`, `url`), a snapshot of its gate facts read just before this run (`facts`: state, head and head revision, the default branch with its head and how many of its commits the pull request lacks (`behind`), whether it merges cleanly, CI at the head, unresolved review threads, and the trusted review verdict with the commit it reviewed and its stamped `contract` coverage), the queue's record (`record`: earlier decisions, with any maintainer's answer, and an approval pinned to the head it approved), and `own_pr`: true for a maintainer's own pull request the queue enrolled, whose work item has no issue and no build record of its own.
- The default branch, its head and its CI there: `$INPUTS.base`.
- The gate command: `$INPUTS.gate`. Append `--pr <url> --head <sha>` to read the gate for a pull request at a head, and `--merge` as well to merge it. It reads the pull request and the default branch fresh, refuses unless the trusted review verdict says Ready at that head, CI is green there, that head contains the default branch's head or the forge reports it merges cleanly, and the default branch's CI is not red, and merges pinned to that head. It doesn't judge review threads; you do (step 4). It prints JSON with its `refusals`. It is the only way you merge: never merge any other way.
- The SDLC policy files this decision names, at `.archon/sdlc/policy/`, falling back to the pack's defaults. This decision names `merge.md`; the pack's defaults are in `$INPUTS.policy_defaults`. Read the default first, then the project's file when it exists: the project's file adds to the default, and where the two conflict, the project's line wins.

Every forge command names the repository with `--repo <host>/<path>`. Run the gate from the checkout's root.

## The default branch first

Judge `$INPUTS.base` before any pull request. Green, or pending: go on; the gate refuses only red. Red: merge nothing this sweep, and say so in each pull request's `reason`. Find what each failing job points at. Red in code none of the pull requests merged since the branch was last green touches gets one rerun of its failed jobs (`gh run rerun <run-id> --failed`), unless the run's attempt number already shows a rerun; then the pull requests `wait`. Red after a rerun, or red in code a recent merge touched, is raised: `base.attention` names the failing checks, every pull request merged since the branch was last green, the one you suspect, and recommends a revert or a fix-forward; its one choice is `hold`. Otherwise `base.attention` is null. `base.reran` is true when you re-ran its failed jobs this sweep. `base.summary` says what you found. A red default branch you neither re-ran nor raised fails the record.

## Decide

Read each pull request's diff and its facts, and class it `clear` or `unclear` by the policy. Measure the diff with git against the merge base: fetch the default branch and the pull request's head from the checkout's remote (`git fetch <remote> <default> refs/pull/<number>/head:refs/remotes/<remote>/pr/<number>`, which also works for a pull request from a fork), then `git diff --stat <remote>/<default>...<remote>/pr/<number>`: the forge's own counts can include commits a merge of the default branch brought in. Then order them, least risk first, with pull requests that touch the same files next to each other and the one the others build on first. Every pull request that can merge this sweep merges this sweep: never hold one back because another is waiting.

Work through them one at a time, in that order. An `own_pr` pull request never goes back to the build queue, because its work item has no build record to return to: wherever a step below says `return`, an `own_pr` pull request is `ask` instead, saying what is wrong and recommending the exact command a maintainer can launch, and its attention item offers no `return` choice.

1. **Stale or missing verdict.** The verdict is not Ready, or it is for a commit other than the head (someone pushed after the review), or it is `unstamped` or `none`: `return`, so a build round reviews it. For an `own_pr` pull request the command is a review, such as `archon workflow run archon-review --input scope=<url>`. The queue never starts that run itself.
2. **Conflict.** The forge reports the merge conflicting. An unclear pull request with no approval that holds is asked first (step 5), and goes back once it is approved. Otherwise: `return`, with a brief to merge the default branch into the head with a normal merge commit (never a rebase), resolve each conflict keeping the intent of both sides, and regenerate any generated file with the script that owns it. For an `own_pr` pull request, the ask names the conflicting files. When the forge has not computed whether it merges (`unknown`, as right after a merge moved the default branch), read the gate again after a short pause; still unknown: `wait`.
3. **CI.** Pending: `wait`, except an unclear pull request with no approval that holds, which is asked (step 5). Red: read the failing jobs' logs and find the files they point at. Red in a file the pull request changes, or in code its change makes reachable, is the change's: `return`. Red in code it does not touch gets one rerun of the failed jobs, and the action is `wait` with `reran` true. When a decision in its record has `reran` true at this `head` and it is red again, it counts as the change's: `return`. Never rerun twice at one head.
4. **Review threads.** Read each open thread's text and judge it. One that raises a defect in what the pull request changes holds it: `return`, with the threads as the evidence. One on code the pull request doesn't change or make reachable doesn't hold the merge, and its `reason` says so.
   Every `return` has a `brief`, which the build queue's next round starts from cold: the pull request by URL and branch, what is wrong with its evidence (each thread's URL, the failing checks with their log lines, the review report's open findings, the conflicting files), and that the issue body is the contract.
5. **Unclear: ask once the verdict is Ready.** An unclear pull request whose verdict is Ready at its head is asked now, even while its CI is pending or it conflicts, unless its record carries an approval that holds (below). A `merge` answer pins the approval to the head you name, and a later sweep merges it once the gate passes. The run raises one question; another unclear pull request is asked in a later sweep, and its decision is `wait`, saying so.
6. **Merge.** A clear pull request, or an unclear one whose approval holds, whose gate passes: run the gate with `--merge` at its head. First, for a pull request that links its issue, check its keyword against the issue: read the issue body (`gh issue view <N> --repo <host>/<path> --json body`), whose latest dated "Current scope" section supersedes earlier ones where they differ. The reference is `Closes #N` only when the verdict's stamped `contract` is `complete` (the review left nothing open; `open` or null means it may not close: an unstamped review never closes the issue, and a fresh review restamps it) and no dated ruling says the issue stays open or the pull request references it without closing it; otherwise it is `Refs #N`. The review report, at the verdict's URL, is context for that judgment, not a second coverage check. When the body says otherwise, in either direction, correct only that reference: read the body (`gh pr view <number> --repo <host>/<path> --json body`), write the whole body with only that reference changed to `$ARTIFACTS_DIR/pr-body-<number>.md`, and apply it with `gh pr edit <number> --repo <host>/<path> --body-file "$ARTIFACTS_DIR/pr-body-<number>.md"`. A body edit does not move the head. When the merge does not land, because the gate refused or the forge queued it, check the keyword again the same way when you next decide it, so an edit someone made meanwhile survives unless the issue contradicts it. When the gate refuses, the facts changed under you: decide again from its refusals. When it fails saying it merged but could not read the merge back, the merge stands: declare it `merged`. When it fails saying the forge accepted the merge but the pull request did not merge, as on a branch whose merges the forge queues, nothing merged: `wait`, saying so. A merge moves the default branch: the next pull request still merges when the forge reports its merge clean. The action is `merged`, with `head` the head it merged at.
7. **Anything else** that only time settles: `wait`, saying what it waits for.

**An approval holds** when it is pinned to the head, or when the only change from the approved head to the head is merges of the default branch and the resolution of their conflicts, and the verdict is Ready at the head. Judge that from `git diff <approved>..<head>` against what the default branch brought in. Anything else in that diff, or any doubt, voids the approval: ask again.

Every pull request gets exactly one decision. A `return` always carries a `brief`, and an `ask` always carries its attention item and, unless it is about an `own_pr` pull request, the `brief` a `return` answer starts from: the record refuses a return without a brief or an ask without its question. Its `number` is the pull request's number (`pr.number`), never its issue's (`item.number`). `head` is always the head your decision is about. `reason` is one line a maintainer can check.

## The attention items

A maintainer reads each without opening the run, so each field stands alone:

- `what`: the pull request and the decision, in plain words.
- `why`: what happens if it is decided either way.
- `recommendation`: the id of the choice you recommend, `why`, the `evidence` it rests on, your `confidence`, and what evidence `would_change` it.
- `choices`, each a kebab-case `id`, a short `label`, what it `does`, its `effect` and a `ruling`. On a pull request, offer at least two: `merge` approves it at the head you name, and a later sweep merges it once the gate passes there; `return` sends it back to the build queue with the brief, and is never offered on an `own_pr` pull request or without a nonblank brief; `park` stops working a build item until the build queue readies it again. On an `own_pr` pull request, `park` stops queue work until a later sweep observes a head different from the head asked about; green CI or a new review at the same head does not bring it back. For a build-owned item, the chosen `ruling` is written into the issue body as a dated scope section, as the contract sentence a returned round reads. An `own_pr` answer stays on the work item's merge decision entry and writes no issue body. Leave `ruling` empty when the choice changes no scope. On a red default branch the one choice is `hold`. The queue adds `other` itself (for a build-owned pull request with a nonblank brief, it returns it with the person's text as the ruling; without a brief it records the text and parks until the build queue readies the item again, starting no build round; on an `own_pr` pull request it parks it instead until a later sweep observes a different head, with the text recorded, because its work item has no build record); don't declare it.
- `if_unanswered`: whether the pull request waits, blocks others, or goes stale as the default branch moves.
- `links`: the pull request, its review comment, the failing runs, and this run.

Declare `summary`: what this sweep merged, sent back and asked, in a few lines.
