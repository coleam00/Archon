# Sweep the Merge Queue

You are the merge queue's one agent for this run. Decide every pull request below: order them, bring the ones behind the default branch up to date with it, merge what policy allows one at a time through the gate, and say what happens to the rest. The next node reads every pull request back from the forge, records your decisions, and raises at most one attention item. You write nothing to the tracker or the state store yourself.

## What you are given

- The pull requests, each with its work item: `$INPUTS.items`. Each has the issue (`item`), the pull request (`pr`, `url`), a snapshot of its gate facts read just before this run (`facts`: state, head and head revision, the default branch with its head and how many of its commits the pull request lacks (`behind`), whether it merges cleanly, CI at the head, unresolved review threads, and the trusted review verdict with the commit it reviewed), the queue's record (`record`: earlier decisions, with any maintainer's answer, and an approval pinned to the head it approved), `prior_report`, the trusted review report a delta review continues from, and `own_pr`: true for a maintainer's own pull request the queue enrolled, which has no issue and no build round behind it.
- The default branch, its head and its CI there: `$INPUTS.base`.
- The gate command: `$INPUTS.gate`. Append `--pr <url> --head <sha>` to read the gate for a pull request at a head, and `--merge` as well to merge it. It reads the pull request fresh, refuses unless the trusted review verdict says Ready (which commit it is for is your call, steps 1 and 2), CI is green there and that head contains the default branch's head, and merges pinned to that head. It doesn't judge review threads; you do (step 4). It prints JSON with its `refusals`. It is the only way you merge: never merge any other way.
- The SDLC policy files this decision names, at `.archon/sdlc/policy/`, falling back to the pack's defaults. This decision names `merge.md`; the pack's defaults are in `$INPUTS.policy_defaults`. A project's file replaces the default whole: when it exists, do not read the default.

Every forge command names the repository with `--repo <host>/<path>`. Run the gate from the checkout's root.

## Decide

Read each pull request's diff and its facts, and class it `clear` or `unclear` by the policy. Measure the diff with git against the merge base: fetch the default branch and the pull request's head from the same remote the sweep pushes to (`git fetch <remote> <default> refs/pull/<number>/head:refs/remotes/<remote>/pr/<number>`, which also works for a pull request from a fork), then `git diff --stat <remote>/<default>...<remote>/pr/<number>`: the forge's own counts are against the pull request's base at its last update and can include commits a merge of the default branch already brought in. A maintainer's approval in its record makes it clear where the policy says it does. Then order them: the default branch's CI first (while it is red, merge nothing and say so in each reason), then clear pull requests, least risk first, with pull requests that touch the same files next to each other and the one the others build on first.

Work through them one at a time, in that order:

1. **Sync.** The gate merges only a head that contains the default branch, so CI judges what the merge produces. Sync only the pull request you are about to merge or ask about, once nothing else would stop it: its verdict is Ready, CI at its head is green and no open thread holds it (step 4). A pull request that waits, goes back or goes to review is not synced this sweep, because every merge before it would make it behind again. When that pull request's head lacks commits of the default branch (its `behind` fact, or `git merge-base --is-ancestor <remote>/<default> <head>` exiting 1 now that an earlier merge moved the branch), sync it: fetch, check out its head detached, merge the default branch with a normal merge commit (never a rebase), and resolve each conflict keeping the intent of both sides. A generated file is never resolved by hand: take either side, then run the script that owns it (the project's `package.json` scripts, or the file's own header, name it) and commit what it produces. Run the focused checks that cover what the resolution touched. Push the merge to the pull request's head branch by name (`git push <remote> HEAD:refs/heads/<branch>`; never force, never let git pick an upstream) and read the remote head back. A pull request from a fork whose author did not allow maintainer edits cannot be synced: ask. A pull request step 4 sends back to the build queue is not synced first. The sync needs a delta review only when you resolved a conflict, because that resolution is new code no review has seen. A merge with no conflict wrote nothing new, even when the default branch changed files the pull request also touches: the Ready verdict carries, CI at the synced head judges the composed result, and you go on to step 5 or 6 with `synced` true. After a conflict, the action is `review`, with `synced` true and `head` the commit you pushed.
2. **Stale verdict.** When the verdict's commit is not the head because of anyone's push other than a clean sync you judged above, or the verdict is `unstamped` (published before verdicts were stamped), or an `own_pr` pull request has no verdict yet (`none`), the action is `review`. With no `prior_report`, that review covers the whole pull request. One delta review runs after you finish, on the first pull request you send to review: set `review_url` to its URL and `review_prior` to its `prior_report`, and leave the checkout clean at that pull request's head. Every other pull request that needs a review waits for the next sweep: action `wait`, saying so.
3. **CI.** Pending: `wait`. Red: read the failing jobs' logs and find the files they point at. Red in a file the pull request changes, or in code its change makes reachable, is the change's: `return`. Red in code it does not touch gets one rerun of the failed jobs (`gh run rerun <run-id> --failed`), and the action is `wait` with `reran` true. When a decision in its record has `reran` true at this `head` and it is red again, it counts as the change's: `return`. Never rerun twice at one head.
4. **What the build queue fixes.** A verdict that is not Ready, an unresolved review thread that raises a defect in what the pull request changes, or red the change caused: `return`, whatever the class, except for an `own_pr` pull request: no build round owns it, so `ask`, with the findings as the attention item's evidence and no `return` choice. Read each open thread's text and judge it: one on code the pull request doesn't change or make reachable, such as one that arrived with a merge of the default branch, doesn't hold the merge, and its `reason` says so. The `brief` is what the build queue's next round starts from cold: the pull request by URL and branch, what is wrong with its evidence (each thread's URL, the failing checks with their log lines, the review report's open findings), and that the issue body is the contract.
5. **Merge.** A clear pull request whose gate passes: run the gate with `--merge` at its head. First, when it links its issue with a non-closing reference (`Refs #N`) and its Ready review left nothing open for a later delivery or an operator check, change that reference to `Closes #N`, so the merge closes the issue: read the body (`gh pr view <number> --repo <host>/<path> --json body`), write the whole body with only that reference changed to `$ARTIFACTS_DIR/pr-body-<number>.md`, and apply it with `gh pr edit <number> --repo <host>/<path> --body-file "$ARTIFACTS_DIR/pr-body-<number>.md"`. A body edit does not move the head. `Closes #N` stands only on a pull request that merges: whenever the merge does not land, because the gate refused or the forge queued it, read the body again and change only that reference back to `Refs #N` the same way before deciding again, so a later review that leaves work open finds `Refs #N` and an edit someone made meanwhile survives. When the gate refuses, the facts changed under you: decide again from its refusals. When it fails saying it merged but could not read the merge back, the merge stands: declare it `merged`. When it fails saying the forge accepted the merge but the pull request did not merge, as on a branch whose merges the forge queues, nothing merged: `wait`, saying so. A merge moves the default branch, so every pull request after it lacks that merge and needs a sync before it can merge. The action is `merged`, with `head` the head it merged at.
6. **Ask.** An unclear pull request whose gate passes, or any case the policy and the facts do not settle: `ask`, with the attention item below. Its `brief` is what a `return` choice launches. A `review` or `wait` that still needs a maintainer's decision afterwards is asked in a later sweep, once the decision is all that is left.
7. **Anything else** that only time settles, such as CI still running: `wait`, saying what it waits for.

Every pull request gets exactly one decision. `head` is always the head your decision is about. `reason` is one line a maintainer can check.

## The default branch after a batch

When you merged anything, wait until every check on the default branch's head after your last merge has concluded (`gh run list --branch <default> --commit <sha>`, then `gh run watch` or `gh pr checks`-style polling with a pause between reads; there is no time limit). Green: `dev.state` is `green`. Red: find what each failing job points at. Red in code none of this batch's pull requests touches gets one rerun of the failed jobs; wait again and judge again, and record the rerun's result in `dev.rerun`. Red after that, or red in code the batch touched, is `red`, and `dev.attention` says so. When you merged but could not wait for those checks, `dev.state` is `unchecked` and `dev.summary` names the merge commit: the next sweep checks it first. When you merged nothing, `dev.state` is `unchecked`, `dev.rerun` `none` and `dev.attention` null: a branch that was already red when the sweep started holds every merge, which each pull request's `reason` says, and you raise nothing for it.

## The attention items

A maintainer reads each without opening the run, so each field stands alone:

- `what`: the pull request and the decision, in plain words.
- `why`: what happens if it is decided either way.
- `recommendation`: the id of the choice you recommend, `why`, the `evidence` it rests on, your `confidence`, and what evidence `would_change` it.
- `choices`, each a kebab-case `id`, a short `label`, what it `does`, its `effect` and a `ruling`. On a pull request, offer at least two: `merge` approves it at the head you name, and the next sweep merges it once the gate passes there; `return` sends it back to the build queue with the brief; `park` stops working it until the build queue readies it again. The `ruling` is written into the issue body as a dated scope section when it is chosen, as the contract sentence a returned round reads; leave it empty when the choice changes no scope. On a red default branch the one choice is `hold`: the queue merges nothing until the branch is green, so the `what` names the failing checks and the pull requests you suspect, and the recommendation says what the maintainer should do, such as revert one of them. The queue adds `other` itself (it returns the pull request with the person's text as the ruling); don't declare it.
- `if_unanswered`: whether the pull request waits, blocks others, or goes stale as the default branch moves.
- `links`: the pull request, its review comment, the failing runs, and this run.

Declare `summary`: what this sweep merged, synced, sent back and asked, in a few lines.
