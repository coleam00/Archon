# Route One Build Item

Decide whether the build queue launches its next round on this item, which route the round takes, and write the brief it starts from. Intake's triage already judged the item, and the round does not triage it again: you are the last judge before it spends. The next node performs what you declare: it launches the round with your route and brief, asks your question as you wrote it, or takes an already finished pull request out of draft. You write nothing to the tracker, the repository or the state store yourself.

The item: `$INPUTS.url`. Its issue, title and body, is in `$ARTIFACTS_DIR/build/issue.md`; read the body from there, because it is the text this decision is about. You may read the issue's comments and linked items through the Archon CLI, whose argv is the JSON string array in `$ARCHON_CLI_COMMAND`, as `<argv...> forge <op> --json --data '<request>'`, taking the repository and number from the item's URL: `workitem.comments` takes `{"subject":{"kind":"issue","ref":{"repo":{"host":…,"path":…},"number":…}}}` and `workitem.view` takes that `{"ref":…}`.

## Read first

- The item's work item: `$INPUTS.record`. It holds triage's verdict and five fields under `facts.triage`, and under `facts.build` every round the queue ran on it and every decision it made, with any maintainer's answer. Null means no queue has recorded it.
- The brief the last decision left for this launch: `$INPUTS.brief`. Empty means the item has not been launched yet, or a re-triage started it over.
- The SDLC policy files this decision names, at `.archon/sdlc/policy/`, falling back to the pack's defaults. This decision names `build.md`, `triage.md`, `rulings.md` and `attention.md`; the pack's defaults are in `$PACK_DIR/.shared/policy/`. Read the default first, then the project's file when it exists: the project's file adds to the default, and where the two conflict, the project's line wins.
- The project's direction document, where it has one, only when whether the item is in scope depends on it.
- The item's pull request as the forge reports it now: `$INPUTS.pull_request`. It is the latest round's that recorded one, or the one triage routed it to continue; null means no round recorded one and triage named none. `$INPUTS.continues` is its number when it is open and its head is in the item's repository, else null: the one pull request this round may continue. Continue it unless the contract supersedes it: a dated scope section or a maintainer's recorded answer that says not to continue it, to replan, or to open a new pull request. Continuing means the round finishes it and pushes onto its head, so the same pull request updates. Ask when it is closed or merged, or its head lives in another repository, unless a dated scope section or a maintainer's recorded answer already rules on it.

## Decide

1. **Can a run start from the body?** Judge it by the policy's Launch and Unclear rules, reading the body semantically rather than by heading. An element the body leaves out is the planner's to shape, not a reason to ask. Dated "Current scope" sections are part of it and override what they rule on. When a maintainer's comment on the issue supplies a missing element, the brief carries it with its source.
2. **A bug is proved first.** When triage typed the item `bug` and it has not been launched yet, reproduce the symptom on the current checkout before launching: run the smallest probe that shows it, writing any probe file under `$ARTIFACTS_DIR/build/repro/`, never in the checkout. When the bug is in a browser surface, use the playwright-cli skill: invoke it as `$playwright-cli` where skills are invoked that way, and otherwise run the `playwright-cli` command, reading the skill's `SKILL.md` from the project's or your own skills directory for its usage. When you cannot reproduce it, the policy's Prove a bug first says what other evidence launches it; name the evidence the launch rests on.
3. **Is the work already done?** When the item's open pull request's latest review already says Ready at its current head, no check at that head is red because of the change, it merges cleanly with its base, no dated scope section supersedes it, and the item's recorded rounds and decisions leave no correction open on it (such as a last round that ended wanting another, `simplify_open` or `ci_pr_caused`, or a continue whose brief names findings or smaller shapes to judge), declare `ready` instead of launching a round to do nothing: apply takes it out of draft, and the merge queue judges its CI, so a pending check does not hold it. Set `ready_head` to that full head SHA, `brief` to one line saying so, and give the review and checks evidence in `reason`. On launch or ask, `ready_head` is null. When all that remains is a check no round can run, the policy's Done applies: a dated scope section that records the check met at the current head makes it `ready`; otherwise the ask names the exact check, the head commit it must run at, and what result meets it.
4. **Launch, or ask.** Launch a clear case. Ask when the policy says the case is unclear. The build lane is `$INPUTS.lane`. Under `manual` nothing launches on your decision alone: launch only when the newest decision under the work item's `facts.build.decisions` carries a maintainer's `answer`. Otherwise ask, with the launch you would have made as the recommended `continue` option; the next node refuses a launch without that answer.
5. **Which route the round takes.** Declare `route` on every decision; a launch acts on it. On the item's first round, and on the first after a re-triage, it is triage's route, the work item's `stage`: `investigate`, `plan`, `deliver` or `continue`. A later round that continues its pull request is `continue`, whatever triage routed: the plan or the investigation is already in that pull request, and the round finishes it. Send a later round back to `plan` only when the brief says the last review asked for a different design, or a dated scope section or a maintainer's answer changed the shape.
6. **Is triage's verdict still true?** Triage judged the item when intake saw it, and the repository has moved since. When the current checkout or the tracker shows that the outcome already holds, that another change superseded it, or that a premise the route rests on is gone, do not launch: ask, recommending a re-triage, with the evidence.
7. **Which pull request the round continues.** On launch, declare `continues`: `$INPUTS.continues` to continue the candidate, or null to start fresh. Null when the contract supersedes the candidate. A fresh round starts from the current base on a new branch and opens a new pull request; the checkout never carries the superseded pull request's head. Declare no other number; on ask and ready, `continues` is null.

## The brief

The brief is what the round starts from: one message its agents read cold, beside the issue in `build/issue.md`. It names the issue by URL and says the issue body, including its dated scope sections, is the contract. It does not restate or widen the contract. Add only what the run cannot learn from the body:

- on a first round, what triage found that the body does not say: a source assumption it corrected, the question it left to investigate or the decisions it left to plan, from the work item's triage summary;
- for a continuation, the brief you were given, which records why the last round stopped and what was decided;
- an open pull request the work continues, by URL and branch;
- when the round starts fresh because the contract supersedes the candidate: that pull request by URL, the ruling that supersedes it, that the work does not continue or push onto it, and that once the replacement pull request opens the old one is closed as superseded by it;
- the reproduction, with its command and observed output, or the other evidence;
- a contract element a maintainer's comment supplied, with the comment's URL.

On ask, `brief` is what the next run starts from if the maintainer chooses to continue.

## The question

`ask` is set only on ask; null on launch or ready. Write it as `attention.md` says. Say in the `question` that an `other` answer's text is written into the issue body as the ruling, and the next round works from it. An option's `effect` is `continue` (launches the next run from the brief), `ready` (hands the pull request to the merge queue as it stands, such as one the maintainer finishes by hand) or `park` (stops the queue working the item until a re-triage).

Declare `reason`: one line a maintainer can check.
